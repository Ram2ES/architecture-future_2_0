# Роадмап изменений технологического ландшафта

## Горизонт планирования

- **Этап 0** (месяцы 1-2): Фундамент - IAM, событийная шина, облачная инфраструктура
- **Этап 1** (месяцы 3-5): Декомпозиция DWH и запуск доменных сред
- **Этап 2** (месяцы 6-8): Портал самообслуживания и Data Products
- **Этап 3** (месяцы 9-12): Подключение партнёров, вывод Legacy

---

## Этап 0. Фундамент (месяцы 1-2)

### Цель
Создать платформенные компоненты, без которых невозможна работа доменов: управление доступом, событийная шина, облачные среды.

### Проекты

**0.1. IAM и разграничение доступа (Keycloak)**

| Параметр | Значение |
|----------|----------|
| Что делаем | Развёртывание Keycloak. Настройка SSO. Создание ролей по доменам: медицина, финтех, ИИ, HQ |
| Ожидаемый результат | Сотрудники финтеха не видят мед. данные; врачи не видят банковские данные. Базовый комплаенс 152-ФЗ и банковской тайны |
| Ответственная команда | Инфраструктурная команда + ИБ |
| Ресурсы | 2 инженера инфраструктуры, 1 специалист ИБ, облачная среда |

**Зачем бизнесу:** решает P6 (нет разграничения доступа). Без IAM невозможно разделение данных по доменам - регуляторный риск блокирует все остальные шаги. Финтех-подразделение с банковской лицензией не может работать, если мед. персонал потенциально видит банковские данные клиентов.

**0.2. Событийная шина (Kafka)**

| Параметр | Значение |
|----------|----------|
| Что делаем | Развёртывание Kafka-кластера в облаке. Определение ключевых топиков: `service.completed`, `payment.status_changed`, `study.ready_for_analysis`, `analysis.completed` |
| Ожидаемый результат | Домены могут обмениваться событиями асинхронно. Apache Camel продолжает работать для Legacy-интеграций |
| Ответственная команда | Инфраструктурная команда |
| Ресурсы | 2 инженера, managed Kafka в облаке |

**Зачем бизнесу:** решает P5 (устаревшая шина). Kafka - фундамент для независимого обмена между доменами. Без неё домены не смогут взаимодействовать после декомпозиции DWH. Асинхронная модель устраняет узкое место - синхронную шину, которая тормозит финтех-транзакции и передачу данных для ИИ.

**0.3. Облачная инфраструктура и IaC**

| Параметр | Значение |
|----------|----------|
| Что делаем | Настройка облачного окружения: Kubernetes-кластеры для доменов, Terraform-шаблоны, сетевая изоляция |
| Ожидаемый результат | Шаблон развёртывания доменной среды: namespace + БД + мониторинг. Каждый домен может быть развёрнут за часы |
| Ответственная команда | Инфраструктурная команда + DevOps |
| Ресурсы | 2 DevOps-инженера, облачные ресурсы |

**Зачем бизнесу:** облако - заявленное стратегическое направление компании. IaC-шаблоны обеспечивают повторяемость: подключение нового партнёра или домена не требует ручной настройки, что сокращает time-to-market.

## Этап 1. Декомпозиция DWH и запуск доменных сред (месяцы 3-5)

### Цель
Вынести данные и бизнес-логику из монолитного DWH в доменные базы данных. DWH переводится в read-only.

### Проекты

**1.1. Домен «Клиники» - выделение данных и сервисов**

| Параметр | Значение |
|----------|----------|
| Что делаем | Миграция данных пациентов, расписания, персонала, инвентаря в доменную PostgreSQL. Перенос бизнес-логики из хранимых процедур в сервисы клиники. Замена PowerBuilder на веб-интерфейс (TypeScript) |
| Ожидаемый результат | Клиника работает автономно. Операторы используют новый интерфейс. Мед. карты и истории болезней изолированы |
| Ответственная команда | Команда домена «Клиники» |
| Ресурсы | 3 бэкенд-разработчика, 2 фронтенд-разработчика, 1 DBA, 1 аналитик |

**Зачем бизнесу:** клиника - ядро бизнеса. Выделение домена позволяет развивать клинические процессы (телемедицина, новые исследования) без зависимости от финтеха. Замена PowerBuilder на веб-интерфейс решает проблему найма (P2): на рынке нет PowerBuilder-разработчиков.

**1.2. Домен «Финтех» - выделение данных и сервисов**

| Параметр | Значение |
|----------|----------|
| Что делаем | Миграция счетов, кредитов, транзакций, скоринга в доменную PostgreSQL. Финтех-сервисы (Golang, Java) переключаются с DWH на доменную БД. Публикация событий в Kafka |
| Ожидаемый результат | Финтех работает автономно. Новые сервисы (страхование, рассрочка) создаются внутри домена без изменений в DWH |
| Ответственная команда | Команда домена «Финтех» |
| Ресурсы | 3 бэкенд-разработчика (Golang/Java), 1 DBA, 1 аналитик |

**Зачем бизнесу:** финтех - самое быстрорастущее направление. Автономность домена позволяет запускать новые финансовые продукты за недели вместо месяцев. Каждый новый сервис (скоринг, страхование, рассрочка) добавляется внутри домена без координации с клиниками или ИИ.

**1.3. Домен «ИИ-сервисы» - подключение к Kafka и S3**

| Параметр | Значение |
|----------|----------|
| Что делаем | ИИ-сервисы переключаются с получения данных через шину Camel/DWH на подписку на Kafka-топики. Мед. изображения читаются из S3. Развёртывание MLflow для версионирования моделей |
| Ожидаемый результат | ИИ получает обезличенные данные из домена «Клиники» через Kafka. Результаты диагностики возвращаются через событие `analysis.completed` |
| Ответственная команда | Команда домена «ИИ» |
| Ресурсы | 2 ML-инженера, 1 дата-инженер, GPU-инфраструктура в облаке |

**Зачем бизнесу:** устраняет задержки в ИИ-диагностике (P5). Врачи получают заключения ИИ быстрее. Независимый цикл: переобучение модели не требует изменений в клинике или DWH.

**1.4. Перевод Legacy DWH в read-only**

| Параметр | Значение |
|----------|----------|
| Что делаем | Запрет на запись в DWH. Все новые данные пишутся только в доменные БД. DWH остаётся доступным для чтения исторических данных |
| Ожидаемый результат | Новая бизнес-логика не добавляется в DWH. Исторические данные доступны на переходный период |
| Ответственная команда | DWH-команда + все доменные команды |
| Ресурсы | 1 DBA, координация с доменами |

**Зачем бизнесу:** фиксирует точку невозврата. После этого шага все изменения происходят в доменах, а не в DWH. Устраняет «очередь на DWH» и взаимные блокировки команд (P1, P4).

## Этап 2. Портал самообслуживания и Data Products (месяцы 6-8)

### Цель
Запустить портал самообслуживания (витрину данных) - прямое требование руководства. Домены публикуют Data Products, бизнес-пользователи строят отчёты самостоятельно.

### Проекты

**2.1. Портал самообслуживания (MVP)**

| Параметр | Значение |
|----------|----------|
| Что делаем | Развёртывание Apache Superset или Metabase. Подключение к Data Products доменов. Конструктор отчётов, дашборды, ролевой доступ через Keycloak |
| Ожидаемый результат | Бизнес-пользователи строят отчёты по загрузке клиник, финансовым показателям, KPI - без обращения к BI-команде. Мед. карты и истории болезней не попадают в витрину |
| Ответственная команда | Платформенная команда + представители доменов |
| Ресурсы | 2 бэкенд-разработчика, 1 фронтенд, 1 аналитик, 1 UX |

**Зачем бизнесу:** прямое требование руководства (задача №1 в task.md). Менеджеры перестают работать «вслепую» - отчёты доступны в реальном времени. Исчезает очередь на BI-команду. Ускоряется принятие управленческих решений.

**2.2. Data Products доменов**

| Параметр | Значение |
|----------|----------|
| Что делаем | Каждый домен формирует свои Data Products: Клиники - загрузка, персонал, услуги; Финтех - транзакции, кредиты, отчётность; ИИ - метрики моделей; HQ - консолидированные KPI |
| Ожидаемый результат | Стандартизированные витрины данных. Каждый Data Product имеет описание, SLA, владельца |
| Ответственная команда | Доменные команды |
| Ресурсы | По 1 дата-инженеру на домен |

**Зачем бизнесу:** Data Products - это «товар» каждого домена. Стандартизация позволяет масштабировать портал на любое количество доменов: при подключении партнёра его Data Product автоматически доступен в витрине.

**2.3. Каталог данных (DataHub)**

| Параметр | Значение |
|----------|----------|
| Что делаем | Развёртывание DataHub. Регистрация Data Products, метаданные, lineage. Бизнес-пользователи находят нужные данные через поиск |
| Ожидаемый результат | Каждый Data Product зарегистрирован, описан, имеет lineage. Бизнес доверяет данным, потому что видит их происхождение |
| Ответственная команда | Платформенная команда |
| Ресурсы | 1 дата-инженер, 1 аналитик |

**Зачем бизнесу:** решает P8 (нет Data Governance). Без каталога бизнес не доверяет отчётам - «откуда эти цифры?». DataHub делает происхождение данных прозрачным и повышает доверие к аналитике.

**2.4. Аналитическая СУБД (ClickHouse)**

| Параметр | Значение |
|----------|----------|
| Что делаем | Развёртывание ClickHouse для OLAP-запросов. Data Products загружаются в ClickHouse. Портал строит отчёты поверх ClickHouse |
| Ожидаемый результат | Сложные аналитические запросы выполняются за секунды вместо часов |
| Ответственная команда | Платформенная команда |
| Ресурсы | 1 DBA, облачные ресурсы |

**Зачем бизнесу:** решает P7 (медленная аналитика). Отчёты, которые раньше строились часами на SQL Server 2008, работают за секунды на колоночной СУБД.

## Этап 3. Подключение партнёров, вывод Legacy (месяцы 9-12)

### Цель
Подключить фарма- и электроника-партнёров. Завершить миграцию с Legacy. Вывести Apache Camel и Power BI с кастомизациями.

### Проекты

**3.1. API Gateway и домен «Партнёры»**

| Параметр | Значение |
|----------|----------|
| Что делаем | Развёртывание API Gateway (Kong). Создание стандартного шаблона подключения партнёра: API-контракт, подписка на Kafka-топики, публикация Data Product |
| Ожидаемый результат | Фарма-компания подключена: получает заявки на поставку (`supply.order_created`), публикует каталог и статусы. Производитель электроники подключен: телеметрия оборудования, заявки на ремонт |
| Ответственная команда | Платформенная команда + партнёры |
| Ресурсы | 2 бэкенд-разработчика, 1 аналитик, координация с партнёрами |

**Зачем бизнесу:** реализует стратегическую цель - интеграцию фармацевтики и производителя электроники. Шаблон подключения снижает стоимость каждого следующего партнёра. Автоматизация заказа препаратов сокращает простои клиник.

**3.2. Вывод Apache Camel**

| Параметр | Значение |
|----------|----------|
| Что делаем | Переключение оставшихся интеграций с Camel на Kafka. Выключение Apache Camel |
| Ожидаемый результат | Единая событийная шина. Нет синхронного бутылочного горлышка |
| Ответственная команда | Инфраструктурная команда |
| Ресурсы | 1 инженер |

**Зачем бизнесу:** снижение затрат на поддержку двух интеграционных платформ. Устранение последнего узкого места в обмене данными.

**3.3. Миграция исторических данных из DWH**

| Параметр | Значение |
|----------|----------|
| Что делаем | Перенос исторических данных из SQL Server 2008 в доменные БД и ClickHouse. Верификация полноты |
| Ожидаемый результат | DWH можно выключить. Все исторические данные доступны в новой архитектуре |
| Ответственная команда | DWH-команда + доменные команды |
| Ресурсы | 2 дата-инженера, 1 DBA |

**Зачем бизнесу:** устраняет затраты на поддержку SQL Server 2008 (лицензии, оборудование, специалисты). Снимает риск безопасности (P2) - снятый с поддержки софт без патчей.

**3.4. Мониторинг и SLA (Prometheus + Grafana)**

| Параметр | Значение |
|----------|----------|
| Что делаем | Мониторинг всех доменных сервисов. SLA-дашборды для медицинских и финансовых систем. Алертинг |
| Ожидаемый результат | Доступность мед. сервисов и финтех-транзакций контролируется в реальном времени. Инциденты обнаруживаются за минуты |
| Ответственная команда | Инфраструктурная команда + SRE |
| Ресурсы | 1 SRE-инженер |

**Зачем бизнесу:** качество медицинских сервисов - жизни пациентов. Качество финансовых - лицензия ЦБ. Мониторинг гарантирует, что новая архитектура работает не хуже, а лучше Legacy.
