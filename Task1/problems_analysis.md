# Анализ проблемных мест и приоритизация

## 1. Целевая архитектура: краткое описание

Целевая архитектура строится по принципу Data Mesh. Вместо одного монолитного DWH данные распределяются по четырём доменам, каждый из которых сам управляет своими данными и публикует аналитические Data Products.

### Домены

| Домен | Владелец | Что хранит и за что отвечает |
|-------|----------|------------------------------|
| Медицина (Клиники) | Подразделение клиник | Пациенты, приёмы, расписание, мед.записи, персонал клиник, инвентаризация |
| Финтех (Банк) | Финтех-компания | Кредиты, счета, платежи, скоринг, финансовая история |
| ИИ-сервисы | ИИ-компания | ML-модели диагностики, анализ мед.изображений, метрики качества моделей |
| Головной офис | Управляющая компания | HR, оргструктура, консолидированная отчётность, инвентаризация |

### Платформенный слой

- **Портал самообслуживания (витрина данных)** - каталог данных, конструктор отчётов, дашборды. Доступ по ролям. Мед.карты, истории болезней и результаты исследований в витрину не попадают.
- **Событийная шина (Kafka)** - замена Apache Camel. Асинхронный обмен событиями между доменами.
- **API Gateway** - единая точка входа, маршрутизация, аутентификация.
- **Data Governance (DataHub)** - метаданные, lineage, политики качества данных.
- **IAM (Keycloak)** - SSO, ролевой доступ к данным.

Legacy DWH на SQL Server 2008 переводится в режим "только чтение" и поэтапно мигрируется в доменные БД.

### Как целевая архитектура закрывает бизнес-сценарии

| Бизнес-сценарий | Как закрывается |
|----------------|-----------------|
| Быстрая отчётность | Data Products каждого домена дают готовые витрины; портал позволяет строить отчёты без обращения к монолитному DWH |
| Независимое развитие финтех и ИИ | У каждого домена своя БД, сервисы и Data Product; изменения в одном не ломают другие |
| Масштабирование под новые бизнесы | Новый домен (фарма, электроника) подключается по шаблону: своя БД, Data Product, публикация в каталоге, доступ через портал |
| Регуляторные требования | IAM + Data Governance дают гранулярный доступ; мед.карты изолированы и не попадают в витрину |
| Отказоустойчивость | Облачная инфраструктура, падение одного домена не задевает другие |


## 2. Проблемные места текущей архитектуры

| # | Проблема | Суть | Какие бизнес-сценарии страдают | Последствия для бизнеса |
|---|----------|------|-------------------------------|------------------------|
| P1 | Монолитный DWH - единая точка отказа | Вся логика и все данные (сотни ТБ) лежат в одном SQL Server 2008. Изменения в одном направлении задевают все остальные. | Отчётность, независимое развитие доменов, масштабирование | Отчёты строятся часами, из-за этого управленческие решения принимаются с задержкой. Доработки для финтеха блокируют ИИ-сервисы. Новое направление не подключить быстро. |
| P2 | Устаревший стек (SQL Server 2008, PowerBuilder) | SQL Server 2008 снят с поддержки, нет патчей безопасности. PowerBuilder - редкая технология, сложно нанимать людей. | Безопасность, комплаенс, качество сервисов | Уязвимости без обновлений, риск утечки данных. Нет доступа к современным возможностям СУБД. Дорогая поддержка. |
| P3 | Нет портала самообслуживания | Пользователи не могут сами строить отчёты. Каждый запрос идёт через BI-команду и кастомизации Power BI. | Скорость решений, time-to-market | Очередь на отчёты, менеджеры работают "вслепую". Аналитики тратят время на рутину вместо сложных задач. |
| P4 | Бизнес-логика зашита в DWH | Значительная часть логики реализована в хранимых процедурах SQL Server. Для нового направления нужно лезть в DWH. | Масштабирование, time-to-market | Подключение фарма-компании требует дорогих изменений в центральном DWH. Высокий риск сломать то, что уже работает. |
| P5 | Устаревшая интеграционная шина (Apache Camel) | Шина - узкое место, всё проходит через неё. Синхронная модель не справляется с ростом нагрузки. | Производительность ИИ и финтех, отказоустойчивость | Задержки финансовых транзакций. ИИ-сервисы получают данные медленно. Если шина падает, встаёт всё. |
| P6 | Нет разграничения доступа к данным | Все данные в одном DWH, нет управления доступом по доменам и ролям. | Комплаенс (152-ФЗ, банковская тайна, врачебная тайна) | Финтех-сотрудники потенциально видят мед.карты, и наоборот. Риск штрафов и отзыва лицензий. |
| P7 | Медленная аналитика | Сотни ТБ в OLTP-движке SQL Server 2008. Много трансформаций. OLTP и OLAP нагрузка не разделена. | Отчётность, качество аналитики | Сложные отчёты занимают часы. Тяжёлые аналитические запросы тормозят работу операторов в клиниках. |
| P8 | Нет Data Governance | Нет каталога данных, метаданных, lineage, стандартов качества. | Доверие к данным, комплаенс, масштабирование | Бизнес не доверяет отчётам. Нельзя отследить происхождение данных. Нет стандартов для подключения нового домена. |
| P9 | Тесная связанность доменов через DWH | Финтех, ИИ, клиники зависят от одной БД и одной шины. Изменение схемы для одного домена ломает другие. | Независимое развитие, time-to-market | Релизы блокируются зависимостями. Координация между командами стоит дорого. |


## 3. Приоритизация проблем

### 3.1. MoSCoW

**Must Have** - без этого не достичь целей через год:

| Проблема | Почему Must |
|----------|-------------|
| P1 - Декомпозиция монолитного DWH | Блокирует масштабирование и независимое развитие доменов. Прямое влияние на выручку через качество отчётности. |
| P3 - Портал самообслуживания | Прямое требование бизнеса (задача номер 1). Без портала нет "витрины данных". |
| P6 - IAM и разграничение доступа | Регуляторное требование: мед.данные и банковская тайна. Без этого нельзя работать с данными разных доменов. Риск штрафов и отзыва лицензий. |
| P4 - Вынос бизнес-логики из DWH | Без этого фарма и электроника не смогут интегрироваться. Напрямую влияет на time-to-market. |

**Should Have** - важно, но можно запуститься с частичным решением:

| Проблема | Почему Should |
|----------|---------------|
| P5 - Замена Apache Camel на Kafka | Критично для производительности финтех и ИИ, но на переходном этапе Camel может работать для части интеграций. |
| P7 - Разделение OLTP/OLAP | Повышает скорость отчётности. Частично решается через P1 (доменные Data Products). |
| P8 - Data Governance и каталог | Важно для масштабирования, но MVP портала может работать без полного каталога. |

**Could Have** - желательно, если хватит ресурсов:

| Проблема | Почему Could |
|----------|--------------|
| P2 - Полная миграция Legacy-стека | SQL Server 2008 в режиме read-only не блокирует развитие. PowerBuilder заменяется в рамках P1. Полная миграция данных - длительный процесс. |
| P9 - Полное устранение coupling | Частично решается через P1 и P5. Полная изоляция - долгосрочная цель. |

**Won't Have** - в этом горизонте нет пунктов, которые совсем не адресуются.

### 3.2. Матрица Эйзенхауэра

|                | Срочно | Не срочно |
|----------------|--------|-----------|
| **Важно**      | **I. Делать первыми:** P1 (декомпозиция DWH), P3 (портал), P6 (IAM и доступ), P4 (вынос бизнес-логики) | **II. Запланировать:** P8 (Data Governance), P9 (полное устранение coupling) |
| **Не важно**   | **III. Делегировать:** P5 (замена Apache Camel), P7 (разделение OLTP/OLAP) | **IV. Фон:** P2 (полная миграция Legacy) |

Пояснения:

**Квадрант I (важно + срочно).** P1, P3, P6, P4 - без них невозможно достичь целей бизнеса через год. P1 и P4 блокируют масштабирование и подключение новых направлений (влияние на будущую выручку). P3 - прямое требование руководства. P6 - регуляторные риски (медицина + банковская лицензия).

**Квадрант II (важно + не срочно).** P8, P9 - важны для долгосрочной устойчивости, но не блокируют запуск MVP через год. Data Governance развивается итеративно. Полная изоляция доменов - результат зрелости Data Mesh.

**Квадрант III (менее важно + срочно).** P5, P7 - влияют на текущую производительность, но частично решаются как побочный эффект от P1. Замену шины можно вести параллельно силами инфраструктурной команды.

**Квадрант IV (менее важно + не срочно).** P2 - Legacy DWH в read-only не мешает развитию. Полная миграция исторических данных ведётся в фоне.


## 4. Связь приоритетов с целями бизнеса

| Цель бизнеса | Какие проблемы критичны | Что будет, если не решить |
|-------------|------------------------|--------------------------|
| Выручка и рост (интеграция фарма + электроника) | P1, P4, P9 | Новые направления не подключатся, упущенная выручка |
| Time-to-market | P1, P4, P5, P9 | Монолитный DWH и coupling замедляют каждый релиз, конкуренты опережают |
| Качество медицинских сервисов | P5, P7 | ИИ-сервисы получают данные с задержкой, диагностика замедляется |
| Качество финансовых сервисов | P5, P6, P7 | Задержки транзакций, риск утечки данных, потеря доверия клиентов |
| Управленческие решения (отчётность) | P1, P3, P7, P8 | Отчёты строятся часами, решения принимаются на устаревших данных |
| Комплаенс и безопасность | P2, P6, P8 | SQL Server без патчей + нет разграничения доступа = утечка данных, штрафы, отзыв лицензий |
