# Разделение на домены

## 1. Принцип разделения

В первом задании определены 4 домена (Клиники, Финтех, ИИ-сервисы, Головной офис) и зафиксирована проблема P4 - бизнес-логика зашита в DWH, что блокирует подключение новых направлений (фарма, электроника). В данном документе эта модель расширяется 5-м доменом «Партнёры», который обеспечивает стандартизированное подключение внешних компаний без изменений в существующих доменах и DWH.

Разделение выполнено по принципу Domain-Driven Design в рамках подхода Data Mesh. Каждый домен соответствует отдельному бизнес-направлению, имеет собственную команду, данные и сервисы. Домены взаимодействуют через стандартизированные контракты (Data Products и события), а не через общую БД.

**Три критерия выделения домена:**
1. Отдельная бизнес-функция (собственная ценность для клиента или компании).
2. Отдельная команда (собственный цикл разработки и релизов).
3. Отдельный регуляторный контекст (собственные требования к хранению и доступу к данным).

---

## 2. Обоснование выделения доменов

### 2.1. Домен «Клиники»

**Владелец:** подразделение клиник.

**Бизнес-сценарии:**
- Ведение приёма пациента: запись, осмотр, назначение лечения.
- Управление расписанием врачей и ресурсами клиники.
- Передача обезличенных данных в домен ИИ для диагностики.
- Передача данных об оказанных услугах в домен «Финтех» для расчётов.

**Почему отдельный домен:** клиника - ядро бизнеса с собственным регуляторным контекстом (врачебная тайна, 152-ФЗ). Медицинские данные требуют особого режима хранения и доступа. Развитие клинических процессов (новые виды исследований, телемедицина) не должно зависеть от финтех-релизов или обновления ИИ-моделей.

---

### 2.2. Домен «Финтех»

**Владелец:** компания с банковской лицензией.

**Бизнес-сценарии:**
- Оформление кредита на лечение.
- Приём платежей за медицинские услуги.
- Скоринг клиента при обращении за кредитом.
- Интеграция с платёжными системами и ЦБ.

**Почему отдельный домен:** банковская деятельность регулируется отдельно (ЦБ, банковская тайна). Финтех-сервисы имеют собственный стек (Golang, Java), собственную команду и независимый цикл релизов. Интеграция нового финтех-сервиса (например, страхование или рассрочка) не должна требовать изменений в DWH - достаточно расширить домен и обновить Data Product.

---

### 2.3. Домен «ИИ-сервисы»

**Владелец:** компания, предоставляющая ИИ-сервисы.

**Бизнес-сценарии:**
- Анализ медицинских изображений (рентген, МРТ) - модель получает обезличенные данные из домена «Клиники» и возвращает результат диагностики.
- Предиктивная аналитика по заболеваемости.
- Рекомендации по лечению на основе истории пациентов.

**Почему отдельный домен:** принципиально иной технологический стек (Python, GPU-инфраструктура) и собственный жизненный цикл (обучение -> валидация -> деплой -> мониторинг). Переобучение модели или добавление нового алгоритма не должно затрагивать клинические или финансовые системы.

---

### 2.4. Домен «Головной офис»

**Владелец:** управляющая компания.

**Бизнес-сценарии:**
- Консолидация отчётности по всем направлениям бизнеса.
- Управление персоналом (найм, увольнение, отпуска).
- Стратегическое планирование на основе KPI всех доменов.

**Почему отдельный домен:** головной офис - потребитель агрегированных данных из всех доменов. Его задача - целостное представление бизнеса, а не операционная деятельность внутри клиник или банка. Изменения в структуре управленческой отчётности не должны затрагивать операционные домены.

---

### 2.5. Домен «Партнёры» (расширение модели из Task1)

**Владелец:** внешние компании (фармацевтика, электроника), интегрированные в экосистему.

**Бизнес-сценарии:**
- Фармацевтика: автоматический заказ препаратов при назначении лечения; управление запасами аптеки клиники.
- Электроника: мониторинг состояния оборудования; автоматические заявки на ремонт/замену.

**Почему отдельный домен:** партнёры - внешние юридические лица со своими системами. Им нужен стандартизированный интерфейс для обмена данными (API-контракт), но не доступ к внутренним системам. Выделение позволяет подключать новых партнёров по шаблону без изменений в остальных доменах - это напрямую решает проблему P4 из Task1 (бизнес-логика зашита в DWH).

## 3. Преимущества для бизнеса

### 3.1. Ускорение вывода продуктов (Time-to-Market)

**Было (монолитный DWH):** любое новое направление требует изменений в центральном DWH - новые хранимые процедуры, трансформации, согласование с другими командами.

**Стало (домены):** новый сервис разворачивается внутри своего домена - своя БД, свои сервисы, публикация Data Product. Другие домены не затрагиваются.

**Пример - интеграция нового финтех-сервиса (страхование):**
1. Команда финтех-домена создаёт микросервис страхования в своём контуре.
2. Сервис подписывается на событие `service.completed` из домена «Клиники».
3. Публикует Data Product «Страховая аналитика» в каталог.
4. Портал самообслуживания автоматически подтягивает новый Data Product.
5. Никаких изменений в DWH, в домене «Клиники» или «ИИ».

**Пример - подключение фарма-партнёра:**
1. Фарма-компания получает доступ через API Gateway.
2. Подписывается на событие `supply.order_created` из домена «Клиники».
3. Публикует свой Data Product (каталог, статусы поставок) через стандартный контракт.
4. Никаких изменений в существующих доменах - шаблон подключения единый.

### 3.2. Снижение зависимости от DWH

**Было:** DWH - единая точка отказа. Все данные, вся логика, все трансформации в одном месте. Доработка для одного направления может сломать другое.

**Стало:** каждый домен владеет своими данными и логикой. DWH переводится в режим «только чтение» и поэтапно выводится из эксплуатации. Новая бизнес-логика создаётся только внутри доменов.

**Конкретный эффект:**
- Исчезает «очередь на DWH» - команды не блокируют друг друга.
- Падение одного домена не останавливает весь бизнес.
- Не нужна команда «хранителей DWH», которая является бутылочным горлышком.

### 3.3. Возможность отдельного развития направлений

- **Клиники** могут внедрять телемедицину, новые виды исследований - без согласования с финтехом.
- **Финтех** может запускать новые продукты (рассрочка, страхование) в своём контуре, используя свой стек и свои релизные циклы.
- **ИИ-сервисы** могут переобучать модели, масштабировать GPU-инфраструктуру, не затрагивая операционные системы клиник.
- **Партнёры** подключаются по единому шаблону: API-контракт + подписка на события + публикация Data Product.

### 3.4. Регуляторная изоляция

Разделение на домены естественно соответствует регуляторным границам:
- **Медицинские данные** (врачебная тайна, 323-ФЗ, 152-ФЗ) изолированы в домене «Клиники».
- **Банковские данные** (банковская тайна, 115-ФЗ) изолированы в домене «Финтех».
- Между доменами передаются только необходимые события, а не сырые данные.
- Для ИИ передаются **обезличенные** данные.

Это напрямую решает проблему P6 из Task1 (нет разграничения доступа к данным).

## 4. Итоги

| Критерий | Монолитный DWH (AS IS) | Доменная архитектура (TO BE) |
|----------|------------------------|------------------------------|
| Time-to-market нового продукта | Месяцы (доработки DWH, согласование) | Недели (внутри домена) |
| Зависимость от DWH | Полная (единая точка отказа) | Нулевая (DWH -> read-only -> вывод) |
| Подключение нового партнёра | Новые таблицы, процедуры, ETL в DWH | Стандартный шаблон, без изменений в других доменах |
| Регуляторная изоляция | Отсутствует (все данные в одной БД) | Естественная (каждый домен = свой регуляторный контекст) |
| Автономность команд | Низкая (все зависят от DWH-команды) | Высокая (каждый домен развивается независимо) |
| Отказоустойчивость | Низкая (DWH падает -> всё стоит) | Высокая (падение домена не затрагивает другие) |
