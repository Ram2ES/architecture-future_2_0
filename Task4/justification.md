# Обоснование конфигурации инфраструктуры

## 1. Выбор облачного провайдера

**Yandex Cloud** выбран как основной IaaS-провайдер:
- Дата-центры на территории РФ - соответствие 152-ФЗ (персональные данные) и требованиям ЦБ для финтех-подразделения с банковской лицензией.
- Нативная поддержка Terraform через официальный провайдер `yandex-cloud/yandex`.
- Полный набор IaaS-компонентов: VM, VPC, S3, NAT Gateway, Security Groups.

## 2. Выбор ресурсов и параметров

### 2.1. Сеть (VPC, подсети, NAT)

| Компонент | Параметры | Обоснование |
|-----------|-----------|-------------|
| VPC `future20-network` | Единая сеть | Все домены внутри одной VPC, изоляция обеспечивается подсетями и Security Groups |
| 6 подсетей | По одной на домен + 2 платформенных (zone-a, zone-b) | Сетевая изоляция доменов. Каждый домен в своём CIDR-блоке - базовое разграничение трафика |
| NAT Gateway | Единый для VPC | VM не имеют публичных IP (кроме API Gateway) - защита от прямого доступа из интернета. NAT обеспечивает исходящий доступ для обновлений и загрузки пакетов |
| Route Table | `0.0.0.0/0 -> nat-gw` | Весь исходящий трафик из приватных подсетей идёт через NAT. Снижает поверхность атаки |
| Статический IP | Для API Gateway | Единая точка входа для партнёров (фарма, электроника). Стабильный IP для DNS-записей |

**Почему 2 зоны доступности:** Kafka-брокеры размещены в zone-a и zone-b. При падении одной зоны второй брокер продолжает обслуживать события. Это критично для финансовых транзакций и передачи медицинских данных в ИИ-домен.

## 3. Декларативный подход (Terraform)

### Почему декларативный, а не императивный

**Декларативный подход** (Terraform HCL) описывает **желаемое состояние** инфраструктуры, а не последовательность команд:

1. **Идемпотентность.** Повторный `terraform apply` не создаёт дубликаты - Terraform сравнивает текущее состояние с описанным и применяет только разницу. Императивный скрипт (bash, Python) при повторном запуске создал бы дублирующие ресурсы.

2. **Граф зависимостей.** Terraform автоматически определяет порядок создания: сначала VPC, потом подсети, потом VM. В императивном подходе этот порядок нужно кодировать вручную.

3. **План изменений.** `terraform plan` показывает, что именно будет изменено, до применения. Императивный скрипт выполняется сразу, без предварительного просмотра.

4. **Управление состоянием.** Terraform хранит state-файл с маппингом ресурсов. Это позволяет корректно удалять, обновлять и переименовывать ресурсы.

### Управление через Terraform vs вручную

Terraform управляет **инфраструктурными примитивами** (VM, Network, Disk, S3, Security Groups, NAT), потому что:
- Они создаются через API облака - Terraform поддерживает их нативно.
- Их конфигурация редко меняется после создания.
- Их легко описать декларативно.

**Вручную** разворачиваются компоненты **прикладного уровня** (установка ПО на VM, DNS, SSL, мониторинг), потому что:
- Установка Kafka/PostgreSQL/ClickHouse зависит от конкретной версии ОС, сетевых настроек, конфигурации кластера - это задача для Ansible, а не Terraform.
- DNS-записи часто управляются корпоративным DNS-провайдером вне облака.
- SSL-сертификаты зависят от корпоративного CA или Let's Encrypt.
- Мониторинг (Prometheus/Grafana) конфигурируется после развёртывания VM.

## 4. IaC: воспроизводимость и масштабируемость

### 4.1. Воспроизводимость

**Проблема без IaC:** инфраструктура создаётся через веб-консоль или одноразовые скрипты. Через месяц никто не помнит, какие параметры у VM, какие правила в файрволе, почему у ClickHouse именно 500 GB диск. При аварии восстановление занимает часы.

**Решение с Terraform:**
- Вся инфраструктура описана в коде - `main.tf`, `variables.tf`, `terraform.tfvars`.
- Код хранится в Git - есть история изменений, review, откат.
- `terraform apply` воссоздаёт идентичную инфраструктуру за минуты.
- Новый инженер читает `.tf`-файлы и понимает архитектуру - код является документацией.

**Пример:** при аварии зоны `ru-central1-a` можно поднять все ресурсы в `ru-central1-b`, изменив значение `zone` в `terraform.tfvars` и запустив `terraform apply`.

### 4.2. Масштабируемость

**Горизонтальное масштабирование доменов:**
Добавление нового домена (например, «Партнёры: фармацевтика») требует:
1. Добавить подсеть в `subnets` в `terraform.tfvars`.
2. Добавить VM для доменной БД в `vm_configs`.
3. Запустить `terraform plan` -> `terraform apply`.

Terraform создаст новую подсеть, VM и Security Group - без ручного вмешательства и без влияния на существующие домены.

**Вертикальное масштабирование:**
Увеличение ресурсов VM (например, ClickHouse с 8 до 16 vCPU) - изменение одного числа в `terraform.tfvars`:
```hcl
cores = 16  # было 8
```
`terraform apply` обновит VM с минимальным простоем.

**Масштабирование Kafka:**
Добавление третьего брокера - добавление записи `kafka-3` в `vm_configs`. Terraform создаст VM в нужной подсети с нужными Security Groups.

### 4.3. Соответствие роадмапу из Task3

| Этап роадмапа | Что создаёт Terraform |
|---------------|----------------------|
| Этап 0 (фундамент) | VPC, подсети, NAT, Kafka VM, Keycloak VM, Security Groups |
| Этап 1 (декомпозиция) | Доменные PostgreSQL VM (clinic, fintech, hq), AI GPU VM |
| Этап 2 (портал) | ClickHouse VM, Portal VM, S3-бакеты |
| Этап 3 (партнёры) | API Gateway VM, статический IP, новые подсети для партнёров |

Каждый этап - это расширение `.tfvars` и `terraform apply`. Инфраструктура растёт вместе с бизнесом.
